# M3 — v0.2.0 可信证据层

## 1. Goal

### Definition of Done

`decay` 能围绕两个核心场景输出可复查证据：

- `diff` 场景：说明本次 diff 对项目复杂度、稳定性和质量产生了哪些可观察影响。
- `doctor` 场景：说明当前项目复杂度债务集中在哪里，哪些区域最值得优先 review 或治理。

v0.2.0 不做“是否可合入”的主观裁决；只建设证据层，并为后续评估层提供可信输入。

### Value Target

作者在 review 任意 PR 或规划质量治理时，不再只看到函数复杂度列表，而是能看到带来源的项目证据：

- 本次 diff 改到了哪些函数、边界和历史高波动区域。
- 当前复杂度债务集中在哪些 file/module/crate，以及为什么这些债务值得优先看。
- 每条 evidence 都能追溯到 source，例如 AST snapshot、diff hunk、git history、decision docs、issue/PR metadata、CI/test run 或 human feedback。

### Key Hypothesis

- **Hypothesis A**: `decay diff <git-ref>` 能在真实 PR review 中提供人工初看遗漏、但用户认可有行动价值的证据。
- **Type**: business value
- **Validation method**: 按真实 PR session 记录人工预判、decay evidence、人工判断和行动结果；出现 ≥2 条人工初看遗漏的 useful evidence，且至少 1 次改变 review / 测试 / 拆分 / 返工动作，则 hypothesis A 初步成立。

- **Hypothesis B**: 增强后的 `decay doctor` 能帮助用户识别比普通复杂函数列表更值得优先治理的 hot complexity debt。
- **Type**: business value
- **Validation method**: 按真实治理规划 session 记录人工 top debt、decay top debt、优先级变化和后续行动；top 3 hot debt 中 ≥2 个被用户认可，且至少 1 次产生实际治理动作，则 hypothesis B 初步成立。

## 2. Plan

### Planned Deliverables

- done: diff hunk 到 Rust function range 的映射，用于 touched function 的 before/after metric delta。
- done: `diff` evidence 输出，覆盖 complexity impact、stability impact、quality impact、history impact。
- done: git history evidence vertical slice，包含 touched files 的 churn、fix-like commits 和 frequent rework。
- done: sensitive area detector vertical slice，覆盖 FFI/public API、storage/migration、protocol/serialization、unsafe、panic/unwrap/expect。
- done: local evidence database vertical slice，包含 changesets、file_changes、evidence_items，并记录 `decay diff` evidence。
- planned: `doctor` evidence 输出，按 file/module/crate 聚合当前复杂度债务。
- planned: 扩展 local evidence database 到 function_changes、git_file_stats 和 dogfood feedback。
- planned: 接入 decision docs、issue/PR/CI metadata 等外部数据源；默认 opt-in。
- doc: 更新 `docs/roadmap.md`、`docs/ops.md`，明确 v0.2.0 验证流程和 evidence 分类。

### Go/No-Go Criteria

| Dimension | Criterion |
|-----------|-----------|
| Functional completeness | `diff` 能输出本次 changed functions 的 metric delta、sensitive area、test gap、git history evidence（team agreement） |
| Functional completeness | `doctor` 能输出 hot complexity debt，按 file/module/crate 聚合并带 git history / boundary tags（team agreement） |
| Quality | `cargo test` 和 `cargo clippy -- -D warnings` 通过（team agreement） |
| Evidence traceability | 每条 evidence 必须记录 source 和 subject，不允许只有抽象判断（team agreement） |
| Performance and stability | 在 mxcore-proposal 规模项目上 evidence 生成可在本地交互式使用；具体阈值待首次实现后实测（pending data） |
| Security | 默认只读本地 git、源码、docs 和本地 SQLite；外部 issue/PR/CI 数据源必须显式 opt-in（team agreement） |
| Maintainability | 证据采集、证据存储、证据展示分层，避免把 rule 和 CLI print 混成一层（team agreement） |

### Estimated Effort

no data（v0.2.0 范围显著大于 v0.1.x；需要在第一轮 vertical slice 后补充估算）

### Decision Path

- **Pass A**: `diff` evidence 在 5-10 个真实 PR 中达到 useful evidence 和 action change 目标后，再考虑风险评分或 merge recommendation。
- **Fail A**: 若 evidence 主要重复人工已知信息或 noise_rate > 50%，暂停评估层，优先修 source、scope、identity 和输出语义。
- **Pass B**: `doctor` evidence 能改变或强化复杂度治理优先级后，继续做趋势和治理计划支持。
- **Fail B**: 若 hot debt 排名与用户判断长期不一致，回到 debt ranking 规则和 git history 权重校准。

### Risks

Dependencies: git diff/function range mapping、稳定 function identity、本地 SQLite schema 演进、项目 docs 结构、真实 PR dogfood。

Risks:

- 引入多数据源后输出变长，用户仍然找不到关键证据。
- git history 的 fix-like / revert-like 规则可能误判，需要保留 source 和 confidence。
- issue/PR/CI 外部数据源差异大，过早接入会拖慢核心 evidence layer。
- 自建数据库若没有清晰 schema 边界，会变成不可维护的日志堆积。
